**작성 기준일** : 2026-09-07
**배포 URL** : `http://<배포 URL>` &nbsp;← **제출 전 반드시 실제 주소로 치환**

> 이 문서는 첨부2 「기능명세서」 양식의 5개 항목에 1:1로 대응하도록 작성했다.
> 기재한 기능은 모두 실제 코드가 동작하는 것이며, 미구현·보류 기능은 1항의 「제외 범위」에 따로 밝혔다.

## 1. MVP 구현 범위

### 1-1. 한 문장 정의

**비상장 외부감사 대상 법인 1곳을 지정하면, DART 감사보고서 원문·국세청 사업자등록 정보·최근 뉴스를 수집해 25개 항목을 5단계 값으로 판정하고, 보고서의 모든 문장에 원문 근거를 붙여 되짚을 수 있게 만든 웹 서비스.**

기존 비상장 기업 조사는 홈페이지·법인등기·DART·재무제표·투자 기사를 사람이 일일이 찾아 맞춰보는 수작업이다. biz-lantern은 이 수집·대조 과정을 자동화하되, **AI가 지어낸 문장이 근거 없이 남지 않도록 생성 결과를 기계가 다시 검증**하는 것을 MVP의 핵심으로 삼았다.

### 1-2. 구현 범위 (실제 동작)

| 구분 | 구현 내용 |
| --- | --- |
| 데이터 수집 | DART 4종(고유번호 전체파일·기업개황·공시검색·공시서류원본), 국세청 2종(사업자등록 상태조회·진위확인), KIPRIS 2종(특허검색·행정처리이력), Tavily 2종(뉴스 검색·본문 추출) 연동 |
| 원문 파싱 | 감사보고서 XML을 자체 파서로 해석. 표의 COLSPAN/ROWSPAN 격자 복원, 계정과목을 라벨이 아닌 ACODE(계정코드)로 식별, 주석 블록을 번호 연속성으로 분할 |
| 통합 조회 | 기업명 1개 입력 → 기업개황 + 감사보고서 최근 3개년 + 국세청 상태 + 특허를 한 화면에 통합 (`GET /api/v1/companies/{기업명}`) |
| 판정 엔진 | 25개 항목을 `확인 / 부재 확인 / 해당 없음 / 읽지 못함 / 확인 불가` 5값으로 판정 (규칙 코드) |
| 근거 시스템 | 근거 조각 10종(API 필드·요약·계정·표·문단·주석·파생계산·출처충돌·뉴스·특허)에 고유 ID 부여, 원문 스냅샷 함께 보관 |
| 이상징후 탐지 | 9종 신호를 규칙으로 탐지, 임계값 판정 과정을 숫자까지 문장으로 노출 |
| 후속 조사 | 신호가 요구하는 조사 항목을 중복 제거해 큐로 생성, 이미 수집한 자료를 다시 읽어 해소 |
| AI 서술 | 판정 결과를 읽을 수 있는 문단으로 서술 후, **기계가 근거 ID·숫자·단위를 재검증**하여 실패 문장은 1회 재생성 후 폐기 |
| 비동기 보고서 | 생성 요청 즉시 202 응답 + report_id 발급, 화면은 3초 간격 폴링으로 완료 감지 |
| 뉴스 요약 챗봇 | LangGraph 5노드 워크플로(검색→병합→재순위→품질판정→본문추출→요약) |
| 배포 | Docker Compose 3서비스(nginx+정적 프론트 / FastAPI / PostgreSQL) 구성 완료 |

### 1-3. 제외 범위 (미구현·보류 — 본 명세서에서 기능으로 주장하지 않음)

| 제외 항목 | 사유 |
| --- | --- |
| 회원가입·로그인·권한 관리 | 인증 도메인 소스 미구현. 서비스 전 화면이 비로그인 공개 |
| 동종업계·경쟁사 비교 분석 | 시장점유율·산업규모에 대응하는 공개 데이터 출처를 확보하지 못함 |
| 투자 라운드·투자 금액 (항목 C-4) | 비상장 법인의 법정 공시사항이 아니며 연동한 외부 출처 없음. 항상 `확인 불가`로 표기 |
| 특허 정보의 **보고서 반영** (항목 D-2) | KIPRIS 특허검색 응답의 키 구조를 실서버로 검증하지 못해 보류. 항상 `확인 불가`로 표기. **단, 기업 검색 화면의 특허 카드·상세 모달은 실제 응답으로 동작하며 이는 2항 4번 기능으로 기재** |
| 기업 상세 페이지 `/companies/{id}` | 화면 시안용 임시 데이터로 동작. 어떤 화면에서도 연결되지 않음 |
| 벡터 검색 / RAG | 임베딩·벡터 검색을 사용하지 않음. 근거 탐색은 결정적 ID 기반 |
| 신용점수·리스크 등급 산정 | 의도적으로 구현하지 않음. "무엇이 더 위험한가"를 점수로 단정하지 않고 "무엇을 더 확인해야 하는가"만 제시하는 설계 |

## 2. 주요 기능 목록

| # | 기능명 | 기능 설명 | 관련 화면 | 구현 상태 |
| --- | --- | --- | --- | --- |
| 1 | 기업 검색 및 기업개황 조회 | 기업명을 입력하면 DART 고유번호를 해소해 대표자·법인등록번호·사업자등록번호·설립일·결산월·주소·업종코드 등 16개 항목을 조회한다. 동명 법인이 여럿이면 후보 목록을 돌려주고, 없으면 미발견으로 안내한다. | 기업 검색 → **기업 기본정보** 카드 | 구현 완료 |
| 2 | 감사보고서 3개년 수집 및 원문 정리 문서 | 감사보고서(F001) 공시를 최근 3개 회계연도까지 내려받아 회계연도·회계법인·접수일·접수번호를 목록으로 보여준다. 기재정정 건은 별도 배지로 구분한다. 연도를 클릭하면 해당 보고서 원문을 표 구조까지 복원한 정리 문서로 하단에 표시한다. | 기업 검색 → **감사보고서** 카드, **감사보고서 정리 문서** | 구현 완료 |
| 3 | 국세청 사업자등록 상태조회 / 진위확인 분리 표시 | 사업자등록번호로 계속사업자·휴업자·폐업자 상태와 과세유형·폐업일을 조회한다. 대표자명·개업일자 대조(진위확인)는 **별개 사실**로 분리해, 진위확인 불일치가 폐업으로 오인되지 않도록 경고를 따로 띄운다. | 기업 검색 → **국세청 사업자 상태** 카드 | 구현 완료 |
| 4 | 특허 조회 및 상세 보기 | 출원인명 기준으로 특허·실용신안을 검색해 건수를 타일로 표시하고, 클릭하면 발명명·출원번호·출원일·등록상태와 행정처리 이력(단계·문서번호·문서일자)을 모달로 보여준다. | 기업 검색 → 특허 타일 → **특허 상세정보** 모달 | 구현 완료 (특허 API 키 미설정 시 0건으로 표시) |
| 5 | 수집 파이프라인 단계별 처리 상태 표시 | 기업개황 조회 → 국세청 확인 → 감사보고서 목록 조회 → 원문 수집 → 정리 저장의 5단계를 각각 성공/실패 배지와 상세 문구로 노출한다. 일부 단계가 실패해도 나머지 결과는 그대로 보여준다. | 기업 검색 → **분석 파이프라인 처리 상태** 카드 | 구현 완료 |
| 6 | 분석 보고서 생성 요청 (비동기) 및 진행 표시 | 「분석 보고서 생성」 버튼을 누르면 즉시 report_id를 발급받아 보고서 화면으로 이동한다. 생성 화면은 무엇을 수집·판정 중인지 안내하고 경과 시간을 초 단위로 표시하며(가짜 진행바를 쓰지 않음) 3초 간격으로 완료를 확인한다. | 기업 검색 → 보고서 화면(생성 중) | 구현 완료 |
| 7 | 25개 항목 5값 판정 | 게이트 4개(DART 등록·외부감사 대상·미제출신고·재무제표 첨부형식), 법적 실체 4개, 재무 6개, 자본구조 4개, 사업실질 4개, 리스크 3개를 각각 `확인 / 부재 확인 / 해당 없음 / 읽지 못함 / 확인 불가`로 판정한다. **"확인해보니 없다"와 "확인하지 못했다"를 절대 같이 취급하지 않는 것**이 판정 체계의 핵심이다. 판정이 `확인`이 아니어도 출처명·기준일·문서링크는 항상 채운다. | 보고서 → **확인 범위와 한계** | 구현 완료 (C-4·D-2는 1-3항에 따라 상시 `확인 불가`) |
| 8 | 근거 추적 (문장 → 근거 조각 → DART 원문) | 본문의 모든 문장에 각주 번호가 붙고, 누르면 그 문장이 인용한 근거 조각이 펼쳐진다. 조각 유형별로 표는 표 그대로, 계정은 연도별 값으로, 파생 계산은 계산식과 상위 근거로, 출처 충돌은 좌우 대조 뷰로 렌더링한다. 어느 경로로 열든 최종적으로 DART 원문 스냅샷과 원문 링크에 도달한다. | 보고서 → 본문 각주 / 근거 토글 | 구현 완료 |
| 9 | AI 서술 + 기계 후검증 | 판정 결과를 6개 절(공시 정보의 일관성·재무·자본 구조·사업과 최근 동향·리스크·이상징후와 추가 조사)의 문단으로 서술한다. 생성 직후 기계가 ① 근거 ID가 그 항목에 실재하는가 ② 문장의 숫자가 인용 근거에 있는 숫자인가 ③ 단위 표기가 허용 범위인가(뉴스만 인용한 문장은 금액·비율 단위 사용 차단)를 검사해, 실패하면 1회 재생성하고 그래도 실패하면 문장을 폐기한 뒤 사유를 남긴다. | 보고서 → **본문**, 항목별 「검증에서 제외된 문장」 | 구현 완료 |
| 10 | 이상징후 탐지 및 후속 조사 목록 | 9종 신호를 규칙으로 탐지한다. 예를 들어 **부채 급증**은 증감률 30% 이상 **그리고** 증감액이 자산총계의 5% 이상이라는 두 관문을 동시에 충족할 때만 발화한다(비율만 보면 작은 계정에서, 절대액만 보면 큰 회사에서 오판하기 때문). 신호마다 임계값 판정 과정을 숫자까지 문장으로 적고, 신호가 요구하는 후속 조사 항목을 중복 제거해 목록으로 제시한다. | 보고서 → **이상징후와 추가 조사** 절 | 구현 완료 |
| 11 | 확인 범위(커버리지) 및 생성 기록 공개 | 감사 여부·수집 보고서 수·확보 회계연도·주석 파싱 성공 여부·주석 결번 목록을 함께 노출한다. 재무 표를 확보하지 못해 이상징후가 0건인 경우와, 실제로 이상이 없어 0건인 경우를 구분하기 위함이다. 수집 단계 로그와 서술 단계에서 발생한 문제도 접이식으로 공개한다. | 보고서 → **확인 범위와 한계**, **생성 기록** | 구현 완료 |
| 12 | 최근 뉴스 요약 챗봇 | 어느 화면에서든 우하단 위젯을 열어 기업명을 입력하면, 뉴스 검색 → 관련도 재순위 → 품질 판정·선별 → 본문 추출 → 중복 사건 묶음 요약을 거쳐 요약문과 출처(언론사·발행일·원문 링크)를 제시한다. 관련 뉴스가 없으면 없다고 답한다. | 전 화면 우하단 **최근 제품 뉴스 분석 AI** 위젯 | 구현 완료 (뉴스 API 키 미설정 시 비활성) |
| 13 | AI 생성 한계 및 투자 책임 고지 | 보고서 상단에 "이 보고서는 AI가 공시 원문에서 생성한 것"임과 투자 판단의 최종 책임이 이용자에게 있음을 상시 고지한다. | 보고서 → 상단 고지 영역 | 구현 완료 |

## 3. 사용자 이용 흐름

### 3-1. 주 흐름 — 기업 검색부터 분석 보고서까지

| 단계 | 화면 | 사용자 조작 | 시스템 동작 | 예상 소요 |
| --- | --- | --- | --- | --- |
| ① | — | `http://<배포 URL>` 접속 | **기업 검색** 화면으로 자동 이동. 로그인 절차 없음 | 즉시 |
| ② | 기업 검색 | 검색창에 기업명 입력 후 **검색** 클릭 | DART 고유번호 해소 → 기업개황·국세청·감사보고서 3개년 원문 수집·파싱 → 특허 조회를 순차 수행. 진행 중에는 스켈레톤 표시 | 최초 조회 수십 초 (원문 캐시가 있으면 수 초) |
| ③ | 기업 검색 (결과) | 결과 확인 | 기업 기본정보 → 감사보고서 + 국세청 사업자 상태 → 분석 파이프라인 처리 상태 → 특허 → 감사보고서 정리 문서 순으로 표시 | — |
| ④ | 기업 검색 (결과) | 감사보고서 목록에서 다른 회계연도 클릭 | 하단 정리 문서가 해당 연도로 교체 (추가 요청 없음) | 즉시 |
| ⑤ | 기업 검색 (결과) | 특허 타일 클릭 | **특허 상세정보** 모달 열림 | 즉시 |
| ⑥ | 기업 검색 (결과) | **분석 보고서 생성** 클릭 | 보고서 ID 즉시 발급, **보고서 화면**으로 이동. 생성은 서버 백그라운드에서 진행 | 즉시 이동 |
| ⑦ | 보고서 (생성 중) | 대기 | 경과 시간이 「N분 N초」로 갱신되고 3초마다 완료 여부 확인 | **약 1분 40초 ~ 2분 10초** |
| ⑧ | 보고서 (완료) | 열람 | 고지 → 법인 기본정보 → 본문 6개 절 → 확인 범위와 한계 → 생성 기록 순으로 표시 | — |
| ⑨ | 보고서 | 문장의 각주 번호 또는 「이 문단의 출처 확인」 클릭 | 그 문장이 인용한 근거 조각(표·계정·주석·파생계산·뉴스)이 원문 스냅샷과 함께 펼쳐짐 | 즉시 |
| ⑩ | 보고서 | 근거의 **원문 열기** 클릭 | DART 공시 원문이 새 창으로 열림 | 즉시 |
| ⑪ | 보고서 | 「← 기업 검색」 클릭 | 기업 검색 화면으로 복귀 | 즉시 |

보고서 화면의 URL(`http://<배포 URL>/reports/{report_id}`)은 그대로 다시 열 수 있으며, 완료된 보고서는 재계산 없이 즉시 표시된다.

### 3-2. 보조 흐름 — 뉴스 요약 챗봇

1. 어느 화면에서든 우하단 원형 버튼 클릭 → **최근 제품 뉴스 분석 AI** 패널 열림
2. 기업명만 입력 후 전송 (예: `트래블월렛`)
3. "뉴스를 검색하고 있습니다" 안내 후, 사건 단위로 묶인 요약과 출처(언론사·발행일·원문 링크)가 표시됨
4. 화면 전환은 발생하지 않으며, 패널을 닫으면 원래 화면 그대로 유지

## 4. AI 및 데이터 처리 방식

### 4-1. AI가 수행하는 역할

AI는 **읽고 고르고 쓰는 일**만 한다. **판정·계산·이상징후 탐지는 전부 규칙 코드가 수행하며 AI는 관여하지 않는다.**

| # | 역할 | 입력 | 출력 |
| --- | --- | --- | --- |
| 1 | 뉴스 관련도 재순위 | 후보 기사의 번호·제목·출처 도메인·본문 요약 300자 | 기사별 관련도 점수(0~1)·순위·중복 그룹 번호·판단 사유 |
| 2 | 뉴스 품질 판정 및 선별 | 재순위 결과 목록 전체 | 검색 품질(충분/불충분)·사유·다음 단계로 넘길 기사 번호 목록 |
| 3 | 뉴스 요약 | 선별된 기사 원문(중복 그룹 단위) | 그룹별 제목·요약문 |
| 4 | 보고서 서술 | 항목별 판정 결과와 근거 조각 묶음 | 문장 배열 + 각 문장의 성격(확인/추론) + 인용한 근거 ID 목록 |

**AI가 하지 않는 것** : 항목 판정, 사칙연산(부채비율·증감률·억원 환산 등), 이상징후 발화 여부 결정, 후속 조사 대상 선정, 위험도 등급 부여.

### 4-2. 환각 차단 설계 (3중)

| 단계 | 방식 |
| --- | --- |
| ① 입력 차단 | AI에게 URL을 주지 않는다. 기사와 근거는 **정수 번호**로만 주고받고, 코드가 그 번호로 원본 객체를 되돌린다. 따라서 AI가 없는 링크를 만들어낼 경로 자체가 없다. |
| ② 역할 제한 | 계산 결과는 코드가 미리 만들어 근거 조각으로 등록하고, AI에게는 "근거에 적힌 표기를 그대로 옮겨라, 반올림·단위환산·직접계산·개수 세기 금지"를 지시한다. |
| ③ 사후 검증 | 생성된 문장마다 (a) 인용한 근거 ID가 그 항목에 실재하는지 (b) 문장에 등장한 숫자가 인용 근거의 숫자 집합에 있는지 (c) 단위 표기가 허용 집합에 있는지 — 특히 뉴스만 인용한 문장은 금액·비율 단위를 통째로 차단 — 를 기계가 검사한다. 실패 시 1회 재생성, 재실패 시 문장 폐기 후 사유 기록. |

또한 **AI가 전부 실패해도 보고서는 완결된다.** 판정값만으로 만들어지는 규칙 기반 정형문이 1층에 남아 있고, AI 서술은 그 위의 2층이기 때문이다.

### 4-3. 사용 모델

- OpenAI 호환 Chat Completions 게이트웨이를 환경변수(`OPENAI_BASE_URL` / `OPENAI_API_KEY` / `OPENAI_MODEL`)로 주입해 사용
- 모든 호출에 **JSON Schema strict 구조화 출력**을 적용하고, 게이트웨이가 거부하는 경우 JSON 객체 모드로 1회 폴백
- 재시도는 429·5xx·타임아웃에 한해 2·5·10초 간격, 서버의 재시도 지시(Retry-After) 우선

### 4-4. 사용 데이터

| 구분 | 출처 | 취득 내용 |
| --- | --- | --- |
| 공시 | DART 고유번호 전체파일 | 전 법인 고유번호·법인명 (14일 캐시) |
| 공시 | DART 기업개황 | 법인명·대표자명·설립일·주소·법인등록번호·사업자등록번호·업종코드·결산월 |

### 4-5. 입력·출력 데이터

- **사용자 입력** : 기업명(문자열) 1건, 챗봇의 기업명 1건. 그 외 사용자가 입력하는 값은 없다.
- **중간 산출물** : 원문 캐시(감사보고서 XML은 접수번호 기준 불변 캐시), 정리 문서(구조화 JSON + 마크다운)
- **최종 출력** : 보고서 JSON 1건(1건당 약 57KB) — 판정 결과 25항목, 서술 6개 절, 근거 조각 약 90~100건, 파생 계산, 이상징후, 후속 조사 목록, 확인 범위, 수집 단계 로그
- **저장** : 보고서·원문 캐시는 서버 파일 볼륨에, 기업 등록 정보는 PostgreSQL에 보관

### 4-6. 개인정보 및 민감정보 처리

| 항목 | 처리 내용 |
| --- | --- |
| 이용자 개인정보 | **수집·저장하지 않는다.** 회원가입·로그인 절차가 없고, 이용자 식별 정보를 받지 않는다. |
| 개인 식별 정보 | 처리 대상은 **법인 대표자 성명** 1건뿐이다. DART 기업개황에 이미 공개된 값을 국세청 진위확인 대조 목적으로 전송할 뿐이며, 별도 프로파일로 축적하지 않는다. |

| 인증키 보호 | 외부 API 인증키가 오류 메시지에 실려 나가지 않도록, 응답·로그·보고서 JSON에 남는 인증 파라미터를 마스킹 처리한다. |
| 원문 취급 | 수집 데이터는 모두 공개 공시·공공데이터·공개 기사이며, 비공개 신용정보·금융거래정보는 다루지 않는다. |

## 5. MVP 검증 방법

### 5-1. 접속 정보

| 항목 | 내용 |
| --- | --- |
| 배포 URL | `http://<배포 URL>` &nbsp;← **제출 전 실제 주소 기재** |
| 테스트 계정 | **불필요.** 로그인 없이 모든 기능 이용 가능 |
| 사전 준비 | 없음. 접속 즉시 기업 검색 화면 |

> 배포 주소에 접근 제한(Basic 인증)을 거는 경우, 여기에 심사용 아이디/비밀번호를 반드시 함께 기재할 것.

### 5-2. 검증 절차 A — 기업 검색부터 보고서 생성까지 (약 2분 30초, 권장)

| 순서 | 조작 | 예상 결과 |
| --- | --- | --- |
| 1 | 배포 URL 접속 | **기업 검색** 화면 표시 |
| 2 | 검색창에 `센트비` 입력 후 검색 | 수 초~수십 초 후 결과 표시 |
| 3 | **기업 기본정보** 확인 | 법인명·대표자·법인등록번호·사업자등록번호·설립일·결산월·주소 등이 채워짐 |
| 4 | **감사보고서** 카드 확인 | 최근 3개 회계연도(2025-12-31 / 2024-12-31 / 2023-12-31) 감사보고서 3건과 회계법인·접수번호 표시 |
| 5 | **국세청 사업자 상태** 확인 | 사업자 상태 `계속사업자` 표시 (진위확인 불일치 경고가 함께 뜰 수 있음 — 대표자·개업일 대조 실패일 뿐 폐업이 아니라는 점이 화면에 설명됨) |
| 6 | **분석 파이프라인 처리 상태** 확인 | 5단계가 모두 성공 배지로 표시 |
| 7 | 감사보고서 목록에서 2024년 클릭 | 하단 정리 문서가 2024년 보고서로 교체 |
| 8 | **분석 보고서 생성** 클릭 | 즉시 보고서 화면으로 이동, 「보고서를 만들고 있다」 + 경과 시간 표시 |
| 9 | 대기 | **약 1분 40초** 후 자동으로 완료 화면 전환 |
| 10 | 보고서 확인 | 판정 항목 **25개**, 본문 **6개 절**, 근거 조각 **90건 이상**, 이상징후 **4건** |
| 11 | **이상징후와 추가 조사** 절 확인 | `영업손실 지속` · `부채 급증` · `재무활동현금흐름 급증` · `투자성 증권 발견` 4건과 각각의 임계값 판정 문장 |
| 12 | 본문 문장의 각주 번호 클릭 | 그 문장이 인용한 근거 조각이 원문 스냅샷과 함께 펼쳐짐 |
| 13 | 근거의 **원문 열기** 클릭 | DART 공시 원문이 새 창으로 열림 |
| 14 | **확인 범위와 한계** 확인 | 확인/미확인 항목 수 요약과 25개 항목별 판정 배지 |

**대조군 확인(선택)** : 2번에서 `업스테이지`로 검색하면 약 2분 10초 뒤 이상징후가 `영업손실 지속` · `매출 증가와 영업현금흐름 악화` · `투자성 증권 발견` · `전기 수치 재작성` 4건으로 **다르게** 나온다. 같은 파이프라인이 기업별로 다른 신호를 잡아낸다는 점을 확인할 수 있다.

### 5-3. 검증 절차 B — 사전 생성 보고서 즉시 열람 (대기 없음)

생성 대기 없이 완성된 보고서만 확인하려면 아래 주소로 직접 접속한다.

```
http://<배포 URL>/reports/<사전 생성 report_id>
```

> ⚠️ **제출 전 작업** : report_id는 서버마다 다르게 발급된다. 배포 서버에서 `센트비`·`업스테이지` 보고서를 각 1회 생성한 뒤 주소창의 실제 report_id를 확인해 위 자리에 기재할 것. (report_id 형식은 `{DART 고유번호}_{생성일시 14자리}`)
